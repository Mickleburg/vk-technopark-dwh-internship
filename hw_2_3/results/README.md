# Результаты

Все три запуска создал scheduler, тип — `scheduled`. Обе задачи завершились успешно:

- 23 января — 961 версия профилей, 53 строки получателей (рассылки 11 — 10, 16 — 23, 23 — 20).
- 24 января — 995 версий, 25 получателей рассылки 21.
- 25 января — 1 036 версий, 22 получателя рассылки 19.

В каждом снимке 100 пользователей. Дублей и пересечений интервалов нет, неизменные атрибуты не создают версий. Получатели совпали с контрольным расчётом на Python. Метаполя заполнены, период и `_run_id` у двух задач совпадают. Подробности — [main_checks.json](main_checks.json), типы полей — [schema_checks.json](schema_checks.json).

После сохранения копий повторил обе задачи за 23 января через Clear. Попытка стала второй, `_run_id` сохранился, `_loaded_at` обновился. Сравнил через `exceptAll` в обе стороны: за 23 января бизнес-поля совпали, за 24–25 января не изменились и метаполя. Экспорт Airflow: [до повтора](airflow_before_repeat.json) и [после](airflow_after_repeat.json).

На fixtures проверил границы: пользователь 1001 попал в рассылку 103 ровно в 12:00 с новой почтой, а в рассылку 104 в 11:59:59 — ещё нет. Пользователь 1003 попадает в рассылку в момент первого события, но не раньше. Повторы состояния, возврат к прежнему логину и пустые результаты тоже проверил — [fixture_checks.json](fixture_checks.json).

Пустые таблицы читаются из Parquet с полной схемой. При пустом пересчёте старые строки партиции удаляются.

В [плане JOIN](task_checks/demo/2026-01-23/build_campaign_recipients/join_plan.txt) — `BroadcastHashJoin` по домену с проверкой интервала. Рассылки передаются через broadcast, чтобы не перемешивать историю профилей.

Parquet: [до повтора](tables/before_repeat/), [после](tables/after_repeat/), [fixtures](tables/fixtures/). Сводки по задачам — `task_checks/`.
