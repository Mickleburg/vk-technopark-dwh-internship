# Домашнее задание 2.3

**SCD2 и исторический JOIN по расписанию**

Курс «Технологии хранения данных DWH» • Шестая, заключительная домашняя работа

В ДЗ 2.1 вы строили историю изменений пользователей, а в ДЗ 2.2 работали с JOIN. Теперь объедините эти расчёты в один DAG Apache Airflow: первая задача строит SCD2-таблицу, вторая использует её для расчёта получателей рассылок. DAG должен запускаться по расписанию, а результаты — содержать метаполя для проверки запусков.

## 1. Исходные данные и окружение

Используйте приложенный стенд: Apache Airflow, Spark и S3-совместимое хранилище RustFS. Можно адаптировать своё окружение из предыдущих работ. Расчёты должны выполняться из DAG без ручного запуска ячеек Jupyter. Версии компонентов и способ запуска зафиксируйте в инструкции к решению.

События профилей: event_time, user_id, user_fio, user_email, user_login. Каждая строка содержит полное состояние профиля. Правила SCD2 берутся из ДЗ 2.1.

Рассылки: data/demo/campaigns.csv из комплекта; файл перенесён из первой задачи ДЗ 2.2 без изменений. Поля: campaign_id, email_domain, send_at, campaign_name. Рассылка предназначена пользователям, чей домен почты совпадал с email_domain на момент send_at.

В приложенных данных поля заполнены, адреса почты корректны, campaign_id уникален, а для одного user_id нет разных событий с одинаковым event_time. Порядок строк и файлов не гарантируется: сортировку задавайте в расчёте. Удаления профилей и разрешение конфликтующих событий в задание не входят.

Для основной сдачи используйте готовый набор data/demo: 6 000 событий, 100 пользователей, seed=42, даты с 1 января по 1 февраля 2026 года. Набор сохраняет схему ДЗ 2.1 и согласован с рассылками ДЗ 2.2. Большой набор из ДЗ 2.2 разрешён как альтернатива; его объём и производительность в этой работе не оцениваются. Инструкции генерации и загрузки находятся в README.md комплекта.

Данные из ДЗ 2.1 с датами по умолчанию в сентябре не подходят: рассылки датированы январём–февралём 2026 года. Перед расчётом проверьте диапазон event_time и не меняйте исходные данные между запусками. Все времена в задании трактуются как UTC. Данные других задач ДЗ 2.2 для этой работы не нужны.

В комплекте есть окружение, исходные данные, генератор и отдельный скрипт проверки подключения Spark к S3. Небольшой набор data/fixtures предназначен для проверки граничных случаев. Самостоятельно напишите DAG, организуйте запуск своих расчётов, передачу периода обработки, заполнение метаполей и сохранение результатов. Порядок запуска стенда описан в README.md.

Обязательные три запуска по расписанию выполняются на demo или выбранном большом наборе. Набор fixtures предназначен для отладки: его дополнительные даты не нужно добавлять в расписание основного DAG. Проверочные примеры из раздела 6 можно показать на нём или на собственном небольшом наборе.

Расчёты и проверки можно писать на Spark SQL или PySpark DataFrame API. Результирующие таблицы — каталоги с файлами Parquet в S3; регистрировать их в Hive Metastore не требуется. Сохраняйте имена и типы полей из условия. Получите контекст запуска средствами Airflow и используйте его в своих расчётах для заполнения метаполей.

## 2. DAG и расписание

Создайте DAG с двумя расчётными задачами и явной зависимостью:

```text
build_user_scd2  →  build_campaign_recipients
```

Вторая задача запускается только после успешного завершения первой в том же DAG run. Обе задачи получают один и тот же интервал обработки и идентификатор запуска из контекста Airflow. Настройте хотя бы одну автоматическую повторную попытку при ошибке и max_active_runs=1.

Расписание — ежедневно в 00:00 UTC. Каждый запуск обрабатывает завершённые сутки [data_interval_start, data_interval_end). Настройте расписание с суточными интервалами данных, например через CronDataIntervalTimetable. Проверьте, что конец интервала больше начала ровно на сутки: поведение одной cron-строки зависит от версии и настроек Airflow.

Для демонстрации ограничьте расписание тремя интервалами ниже и включите catchup. Scheduler должен сам создать и выполнить эти исторические запуски; ждать три календарных дня не требуется. Одних запусков вручную или через тестовую команду недостаточно.

| Дата расчёта D | Начало интервала, UTC | Конец интервала, UTC |
| --- | --- | --- |
| 2026-01-23 | 2026-01-23 00:00:00 | 2026-01-24 00:00:00 |
| 2026-01-24 | 2026-01-24 00:00:00 | 2026-01-25 00:00:00 |
| 2026-01-25 | 2026-01-25 00:00:00 | 2026-01-26 00:00:00 |

Дата расчёта D — дата начала интервала в UTC. Для отбора данных используйте границы интервала, а не текущее время выполнения задачи. Источники на время проверки считаются неизменными; обработка поздно поступивших событий в эту работу не входит.

В Airflow 2.10.5 с CronDataIntervalTimetable граница end_date включительно ограничивает логическую дату запуска — начало интервала. Не путайте её с концом последних обрабатываемых суток из таблицы. Исторический запуск выполняется сейчас, но обрабатывает свой январский интервал.

## 3. Первая задача: построение SCD2

Для каждого D постройте снимок всей истории пользователей по событиям event_time < data_interval_end. На первом запуске также учитывается история до data_interval_start. Отбор только событий текущих суток потеряет ранее созданные профили.

Сохраните снимок в отдельную партицию таблицы user_scd2 в S3, например user_scd2/snapshot_date=D/. Допускается полностью пересобирать этот снимок из исходных событий: инкрементальное обновление не является обязательным. Каждый снимок должен читаться независимо от других дат.

Бизнес-поля результата: user_id, user_fio, user_email, user_login, valid_from, valid_to, is_current — с тем же смыслом, что в ДЗ 2.1. Добавьте snapshot_date и метаполя из раздела 5.

Типы полей: user_id — bigint (вмещает uint32 из ДЗ 2.1); user_fio, user_email, user_login — string; valid_from и valid_to — timestamp; is_current — boolean; snapshot_date — date. NULL допустим только в valid_to актуальной версии.

Сохраните правила ДЗ 2.1: события упорядочены по event_time; новая версия появляется только при изменении ФИО, почты или логина; интервалы [valid_from, valid_to) не пересекаются; последняя известная версия имеет valid_to=NULL и is_current=true. У каждого пользователя, присутствующего в снимке, ровно одна такая версия.

Первая версия начинается в event_time первого события пользователя. Для следующих версий valid_from равен времени события, изменившего хотя бы один из трёх атрибутов. valid_to предыдущей версии равен valid_from следующей версии. Повтор события с теми же атрибутами не создаёт и не закрывает версию.

is_current здесь означает последнюю версию среди событий, известных к концу выбранного интервала. Не закрывайте её границей суток. Будущие события не должны попадать в снимок. Ключ строки внутри снимка — (user_id, valid_from); при чтении нескольких снимков к ключу добавляется snapshot_date.

Сравнивайте состояние с предыдущим событием пользователя. Возврат A → B → A образует три версии, даже если последняя повторяет атрибуты первой. Сохраняйте исходные значения атрибутов; приведение домена к нижнему регистру нужно только для сравнения при JOIN.

## 4. Вторая задача: получатели рассылок

Прочитайте сохранённый первой задачей снимок user_scd2 именно для D. Из campaigns.csv выберите рассылки, для которых data_interval_start ≤ send_at < data_interval_end. Выполните JOIN, найдя всех пользователей, подходящих каждой рассылке.

Строка попадает в результат, если одновременно выполнены условия:

- домен user_email в выбранной версии равен email_domain рассылки;

- valid_from ≤ send_at;

- send_at < valid_to либо valid_to IS NULL.

Домен — часть адреса после @; сравнивайте домены в нижнем регистре. Выбирать только is_current=true нельзя: требуются атрибуты на момент рассылки. Если в этот момент профиль ещё не существовал или домен не совпал, пользователь в результат не попадает.

Сохраните таблицу campaign_recipients в S3 с партицией calculation_date=D. Поля: campaign_id, campaign_name, send_at, email_domain, user_id, user_fio, user_email, user_login, user_valid_from, user_valid_to, calculation_date и метаполя из раздела 5. Поля user_valid_from и user_valid_to берутся из присоединённой версии SCD2. Одна строка — один получатель одной рассылки; дубли (campaign_id, user_id) недопустимы.

Типы полей: campaign_id и user_id — bigint; send_at, user_valid_from, user_valid_to — timestamp; calculation_date — date; остальные бизнес-поля — string. NULL допустим только в user_valid_to. Поля рассылки и профиля сохраняются в исходном виде, включая регистр символов.

Пример: до 11:00 почта пользователя — a@example.com, с 11:00 — a@mail.example. Для рассылки в 10:00 подходит домен example.com, а ровно в 11:00 — mail.example. Проверка относится к состоянию профиля в send_at, даже если расчёт выполняется значительно позже.

Приложите план выполнения JOIN и кратко объясните выбранную стратегию, опираясь на ДЗ 2.2. Отдельное сравнение производительности всех стратегий в этой работе не требуется.

## 5. Метаполя и повторные запуски

В обеих результирующих таблицах каждая строка должна содержать следующие непустые поля:

| Поле | Тип | Значение |
| --- | --- | --- |
| _dag_id | string | Идентификатор DAG из контекста Airflow. |
| _run_id | string | Идентификатор DAG run из контекста Airflow; одинаков для обеих задач одного запуска. |
| _task_id | string | Идентификатор задачи, записавшей строку. |
| _data_interval_start | timestamp | Начало интервала данных запуска, UTC. |
| _data_interval_end | timestamp | Конец интервала данных запуска, UTC. |
| _loaded_at | timestamp | Фактическое время формирования результата текущей попыткой задачи, UTC. |

Метаполя описывают расчёт снимка или партиции, а valid_from и valid_to — историю профиля. Поэтому все строки снимка, включая старые версии, получают метаполя запуска, который построил этот снимок. Не включайте метаполя в сравнение атрибутов при обнаружении изменений SCD2. _loaded_at зафиксируйте один раз на попытку задачи.

Повторное выполнение задач за тот же D должно заменять результат только этой даты, сохранять остальные партиции и не добавлять дублей. Бизнес-поля должны совпадать с результатом до повтора; _loaded_at может измениться, а _run_id — только если создан новый DAG run. При повторе задач внутри существующего DAG run его _run_id сохраняется.

Вторая задача обязана читать результат первой за тот же D, а не последний доступный снимок. Не передавайте содержимое таблиц через XCom: между задачами достаточно передать путь к результату и параметры запуска. Если рассылок или получателей за период нет, задача должна корректно завершиться с нулевым результатом; повторный расчёт не должен оставлять старые строки этой партиции.

Пустой результат также сохраняйте как читаемый Parquet с полной схемой, включая метаполя. Если до конца интервала нет событий профилей, снимок SCD2 будет пустым. Нулевые количества подтверждайте чтением результата или логом задачи: у пустой таблицы нет строк, из которых можно собрать сводку метаполей.

## 6. Что проверить и сдать

Перед сдачей выполните три запланированных запуска. Сохраните копии результатов, затем повторно выполните обе задачи первого запуска, когда результаты последующих дат уже существуют. Приложите проверочные SQL-запросы или код DataFrame API и результаты:

1. Для каждого снимка SCD2: количество строк и пользователей, отсутствие пересечений интервалов и дублей ключа, ровно одна текущая версия на пользователя, отсутствие лишних версий при неизменных атрибутах.

2. Для каждой даты витрины: количество строк и получателей по campaign_id, отсутствие дублей (campaign_id, user_id), соответствие домена и исторического интервала. Покажите небольшие контрольные примеры JOIN, включая смену домена, точное попадание в valid_from/valid_to и дату до первого события пользователя. Эти примеры можно проверить на отдельном небольшом наборе данных.

3. Для обеих таблиц: сводку по _dag_id, _run_id, _task_id, границам интервала с количеством строк и min/max(_loaded_at). Проверьте отсутствие NULL в метаполях и согласованность интервалов и _run_id между задачами каждого запуска.

4. Для повторного расчёта: сравнение всех бизнес-полей и полей даты до и после, исключив только шесть метаполей. Например, используйте EXCEPT ALL или exceptAll в обе стороны с одинаковым порядком столбцов. Одного совпадения количества строк недостаточно. Для остальных дат подтвердите сохранение всех полей, включая метаполя.

На проверку передайте:

- код DAG, код двух расчётов и проверок (SQL или DataFrame API);

- доступные проверяющему результаты обеих таблиц за три даты либо выгрузку этих партиций;

- скриншот или экспорт из Airflow с тремя успешными запусками, их типом scheduled, идентификаторами и состояниями обеих задач; также подтверждение повторного выполнения;

- краткий отчёт с выбранным набором данных, проверками выше и планом JOIN. Вместо личного .env приложите .env.example; учебные значения по умолчанию из комплекта можно сохранить, реальные пароли и ключи доступа не прикладывайте.
